# Audit guide

## Candidate evidence

Before proposing a repair, consolidation, or deletion, read the full test, production owner, entry points, relevant callers and callees, overlapping tests, and CI routing. Inspect relevant history to establish why the test exists. Check dependency source or types when the judgment depends on dependency behavior.

Record each candidate's:

- Exact name and location, asserted contract, and detectable regression.
- Non-test callers of any production seam the removal could retire.
- Keeper location and distinct risks, or evidence that no intended contract exists.
- Assertions to transfer before removal, including exceptional parameter rows.
- Relevant history, uncertainty, and focused validation command.

When evidence is unavailable, record the gap and preserve the candidate.

## Classification

- **Keep:** name the contract and credible regression it detects.
- **Repair:** retain the contract; identify ineffective or misleading proof and its replacement.
- **Consolidate:** name the keeper and assertions it must absorb before removal.
- **Delete:** name the remaining proof or establish that no intended contract exists.
- **Unresolved:** name missing evidence and preserve the test.

Judge assertions rather than names. A test named for persistence may inspect a mock store that production never writes.

## Junk patterns

Treat these as candidates, not automatic deletion rules:

- Self-comparisons, assertion-free probes, and expectations generated by the subject under test.
- Mocks or fixtures that implement the outcome production is supposed to produce.
- Private-state, helper-call, internal-order, and source-shape assertions that fail under behavior-preserving refactors.
- Repeated cases or layers with no distinct failure mode.
- Copied manifests, export inventories, or constants with no independent contract.
- Tests asserting removed code stays absent solely because it was removed.
- Tests repeating guarantees supplied entirely by a dependency or type checker.
- Negative cases that fail at an unrelated guard or never reach the intended rejection.
- Fixtures that fabricate receipts, callback order, or persistence effects the owner should produce.

## Retention exceptions

A suspicious form can still protect an independent contract:

- **Absence:** an unsafe API remaining unavailable can be a security requirement. A module remaining absent from its old path is usually migration history, unless that path itself carries a compatibility requirement.
- **Source or byte checks:** exact protocol bytes, published package contents, architectural boundaries, and generated cross-language interfaces can require static proof. Prefer checks that survive identifier-only refactors unless the identifier is itself public.
- **Multiple layers:** a domain test and an HTTP test can share a business outcome while catching different defects. Name the transport or lifecycle risk before consolidating them.
- **Observable calls and order:** charging a payment provider once or acknowledging only after durable storage can be public contracts. Internal helper selection is not the same thing.
- **Dependencies and types:** verifying a library repeats its own guarantee adds little; verifying our configuration or integration honors that guarantee can earn a keeper. Compile-time tests can protect a published type API.
- **Test support:** fixtures and teardown can provide necessary isolation. Remove helpers and production seams only when their remaining consumers and contracts are accounted for.

## Examples

**Duplicate or distinct?** Two tests compute the same cart total through the same domain API with equivalent inputs: consolidate. An HTTP test also proves decimal serialization: retain that distinct contract.

**Fabricated or independent?** Mocking `checkout` to return `confirmed` and asserting that result proves the mock. Supplying a payment-provider response and asserting that real checkout produces a retrievable order exercises production behavior.

**Historical or required absence?** A check that `legacy.ts` is gone records a past edit. A package-contents check that excludes private credentials protects an ongoing release contract.
